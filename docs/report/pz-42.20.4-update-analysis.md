## 1. 官方 42.20.4 動了什麼（bytecode 實證）

全 jar 26,020 entry：**變更 22 class、零新增、零移除**——微型更新。主題＝
**惡意封包長度驗證（反 DoS/反作弊加固）**：

- `LoadPlayerProfilePacket.parse`：讀 profile buffer 前新增 `size<0 || size>remaining()`
  檢查，不合法 → `warn("LoadPlayerProfile: invalid character size…")`＋`isExist=false`，
  取代舊版盲目 `newarray byte`（malformed packet 可觸發任意大小配置）。
- `GameServer.receiveSyncRadioData`：頻道陣列讀取前加 `iflt`／上限
  `MAX_RADIO_DATA_SIZE=32767`（新 private 編譯期常數，bytecode 內聯 `sipush 32767`）／
  `remaining()/4` 三重驗證（82→95 指令）。
- `RCONServer` 家族 4 class：同主題加固（新驗證位於 `RCONServer$ClientThread`，
  不在我方 loose 清單——混跑期間即已生效）。
- `J2SEPlatform.setupEnvironment`：**刪除 `LuaCompiler.register` 與 `serialize.lua`
  載入**（91→46 指令）、`LuaCompiler.register` 方法自 class 移除——vanilla 拿掉
  Kahlua compiler 註冊；`ZomboidFileSystem.normalizeToPath` 在 `toAbsolutePath` 後多
  一次 `Path.normalize`。
- `GameServer` 主檔＋6 個 nested class：**常數池重排假差異**。190 個 method（含
  `static {}`）經正規化後真差異僅 `main`（唯一實質差異＝build hash 字串
  `70207f62e0`→`b0bbce05d5`）與 `receiveSyncRadioData`（上述）；nested 全部指令等價。
- 其餘（`Core`、`GitVersion`、`MainScreenState`、`AttachmentEditorState`、
  `ISWorldObjectContextMenuLogic`、generation builders）：版本字串／BSM recipe
  （`Core` 的 concat recipe `.3`→`.4`）／私有成員增減等零星變化。

措辭修正（codex 審查）：本版**有**新增/移除私有成員（`MAX_RADIO_DATA_SIZE`、
`ContextEntryBuilder` 私有 field/method），「未改資料結構」僅在「與 loose class
互動的結構形狀」範圍內成立。

## 4. uninstall 假死事故（本次最重要教訓）

**「uninstall 只影響下次重啟、不影響執行中 JVM」的假設不成立。** JVM 的符號引用是
**lazy resolution**：已載入 class 的未執行路徑，其常數池引用在**首次執行到該指令**時
才觸發 class 載入。uninstall 刪檔後，任何「已載入 patched class → 尚未載入的 helper」
冷路徑都是地雷：

- 本次實證：`ServerChunkLoader$SaveChunkThread.addLoadedJob`（W9 patched，開服即載入）
  的 `ChunkSaveIsolation` 引用，在主迴圈熱路徑早已 resolve；但
  `ServerMap$ServerCell.Save → ServerChunkLoader.addSaveLoadedJob → addLoadedJob`
  這條 **worker 執行緒冷路徑**直到 uninstall 後 ~40 分鐘才首次執行——4 條
  `ServerMap$WorkerThread` 在同一毫秒內 `NoClassDefFoundError` 未捕獲死亡，
  主迴圈等 worker 產出永久凍結（W15 看門狗 12 張快照，`ticks=0`），全服假死
  ~28 分鐘直到排程重啟。
- （同機制的無害前兆：uninstall 前 log 已有 4 筆同座標 `ClassNotFoundException`
  ——當時被主迴圈 catch；worker 執行緒版本沒有 catch，直接死執行緒。）

**修正後的止血 SOP**：發現「新 jar＋舊 loose class」混跑時——
1. uninstall 檔案（防下次重啟再混跑）；
2. **立即安排受控重啟**（凍結窗最短化），因為「已載入 patch＋helper 檔案已刪」是比
   混跑**更不穩定**的狀態（冷路徑 lazy resolve 全是地雷）；重建驗證通過後裝回、
   同一次重啟直接帶新 patch 起來最優；
3. 若無法立即重啟，至少監看 console 的 `ClassNotFoundException`／
   `NoClassDefFoundError` 與 W15 看門狗輸出，出現即 pkill -9 重啟。
